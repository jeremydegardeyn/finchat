# ADR-0023 — Agent registry, per-agent identity, and lifecycle

- **Status:** Accepted
- **Date:** 2026-08-04
- **Deciders:** Principal Data Architect
- **Context tags:** Agent governance, non-human identity, auditability, AI control framework

## Context

FinChat runs ten agents — five loan agents, the Banking Assistant, three steward roles,
and the managed analyst Data Agent — and until now every one of them acted as the **same
shared service account** (`finchat-<env>-agent`). Three things follow from that, none good:

1. **Nothing in the audit trail distinguishes them.** Every tool call resolves to one
   identity, so "which agent read this account, and who is accountable for it" is not
   answerable from the logs.
2. **Permissions are the union of what every agent needs.** The Notification Agent, whose
   only job is to send a message, holds BigQuery read on the loans dataset because the
   Approval Agent needs it.
3. **There is no population to manage.** Agents are code inside an application, so they
   are never provisioned, reviewed, or deprovisioned as a governed set.

The regulatory backdrop makes this worse rather than better. Revised model risk guidance
(**SR 26-2 / OCC Bulletin 2026-13**, 17 April 2026) rescinded SR 11-7 and states that
generative and agentic AI "are not within the scope of this guidance." There is no
supervisory framework demanding an agent inventory, and no published reference
architecture from any US bank for an agent registry, agent identity scheme, or agent
gateway. The absence of a template is the reason to write one down, not a reason to wait.

## Decision

Treat agents as a **managed population of non-human identities**, governed on the same
disciplines as privileged human access.

### 1. A registry that is source code

`scripts/agents_catalog.py` is the single source of truth — the same pattern
`products_catalog.py` already establishes for data products. Each agent declares its
owner, supervising business area, risk tier, distinct identity, **tool allow-list**, data
scope, model reference, whether its action is consequential, whether a human gate applies,
and its recertification date.

Everything else is generated from it:

| Artifact | Generated by | Purpose |
|---|---|---|
| `infra/envs/*/agents.auto.tfvars.json` | `agents_catalog.py --emit-tfvars` | Terraform's agent map — SAs cannot drift from the registry |
| `finchat_platform_<env>.agent_registry` | `agent_registry_bootstrap.py` | Queryable current state for the Admin UI and an examiner |

### 2. A distinct identity per agent, used by impersonation

Every agent gets its own service account. Because ADK sub-agents share a process, the
runtime cannot simply *be* five identities at once — so the runtime holds no agent
privileges and instead **mints short-lived credentials for the acting agent** via
`roles/iam.serviceAccountTokenCreator`. This is not a new pattern for FinChat: the
anonymous analyst tier ([ADR-0019](0019-end-user-credential-propagation.md)) already
works this way.

### 3. A CI gate that reads the code, not the intention

`verify_agent_registry.py` parses the agent source with `ast` and compares it to the
registry. It fails the build on:

| Check | Fails when |
|---|---|
| `DRIFT-1` | an agent is constructed in code but not registered |
| `DRIFT-2` | a registered agent no longer exists in code |
| `DRIFT-3` | the code grants a tool the registry never approved |
| `REG-1` | an agent lacks owner, business area, risk tier, identity or data scope |
| `REG-2` | two agents share a service account |
| `REG-3` | an agent takes consequential action with no human-in-the-loop gate |
| `LIFE-1` | recertification is overdue |
| `PIN-1` | *(warning)* the agent runs a floating model alias — see [ADR-0022](0022-model-version-pinning.md) |

`DRIFT-3` is the one that converts the registry from an inventory into a control. Adding a
tool to an agent is a permission grant; here it cannot happen without a registry change,
which is a reviewable diff with a named owner attached.

### 4. Recertification on the privileged-access cycle

HIGH-tier agents recertify every 90 days, MEDIUM every 180, LOW every 365. Overdue fails
the build; due within 14 days warns. The cadence deliberately matches privileged human
access, because the argument for treating agents as a lesser category is weak — several
of these agents can reach production financial data.

### 5. Attribution as evidence

`agent_action_log` is append-only, partitioned by day and clustered by agent, and records
the acting identity, the accountable owner at time of action, the tool, **whether the tool
was inside the allow-list**, the human approver where a gate applied, and the model version
that actually served. That last pair is what makes "who authorised this agent to take this
action" answerable without reading application logs.

## Consequences

**Positive**

- Every action attributable to one agent and one accountable human.
- Tool permissions are least-privilege per agent instead of a union.
- A tool cannot be granted without a reviewed registry change.
- Agents are provisioned, recertified and deprovisioned as a governed population.
- The registry is queryable evidence, refreshed on every deploy, that can be shown directly.

**Negative / accepted**

- **Ten service accounts instead of one.** More IAM surface; justified because attribution
  is the whole point.
- **The catalogue must be regenerated after every change.** CI fails on a stale projection,
  so the failure mode is a loud build rather than silent drift.
- **Impersonation adds a token exchange per agent action.** Latency cost is small relative
  to model latency, but it is not zero.
- **The registry cannot detect an agent that never reaches the AST scanner** — a dynamically
  constructed agent, or one built by a framework FinChat does not parse. `DRIFT-1` covers
  ADK constructors and declared function entrypoints only. This is a real limit, stated
  rather than papered over.

## Alternatives considered

- **Google Agent Registry (managed).** Rejected for now on churn grounds: Cloud API Registry
  was announced as the tool-governance answer in December 2025 and its MCP support was
  deprecated by July 2026 in favour of Agent Registry. Depending on it would put a control
  on a component that has been reworked once inside a year. The design deliberately depends
  on stable primitives — IAM identity, BigQuery evidence, a CI gate — and treats the managed
  product as adoptable later behind the same registry contract.
- **One SA per product rather than per agent.** Cheaper, but it does not answer the question
  the registry exists to answer; the loan agents would remain mutually indistinguishable.
- **Runtime enforcement of the allow-list instead of a CI gate.** Complementary, not a
  substitute — a runtime check catches an unregistered call, a CI gate stops it shipping.
  The `authorized` column in `agent_action_log` is where runtime enforcement lands next.
